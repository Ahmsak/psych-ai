## Проблема 1 — «no psychologist utterances» (0 реплик психолога)

### Наблюдение
- Отчёт: Session/Orchestrator = WARNING `['no psychologist utterances']`;
  статистика utt=19, psy=0, cli=19.
- `mic_segments.json` = `[]` (пусто) → Conversation не получает ни одной
  реплики микрофона → 0 реплик психолога.
- НО `mic_transcription.txt` НЕ пуст (10 строк текста).

### Измерения (реальные, из WAV)
- mic.wav:   dur=351.3s, rms=71.3, peak=1193 (~3.6% от 32768),
  доля |amp|>200 = 2.5%.
- loopback.wav: dur=319.2s, rms=1974.2, peak=27423, доля|amp|>200 = 23.5%.
- metadata mic.rms_max=386.9; loopback.rms_max=9596.9.
- Прямой прогон сегментного пути по mic.wav: `m.transcribe(vad_filter=True)`
  → 0 сегментов; `vad_filter=False` → 0 сегментов.

### Причина
Два независимых пути транскрипции дают разный результат на слабом сигнале:
1. `mic_transcription.txt` пишется через StreamingTranscriber (Sprint 3):
   фиксированные окна отдаются Whisper, который на почти-тишине
   ГАЛЛЮЦИНИРУЕТ текст («Продолжение следует...», «До свидания»).
2. `mic_segments.json` пишется через `m.transcribe()` по всему файлу
   (Sprint 7 data-слой): на таком слабом сигнале честно возвращает
   0 сегментов.

Первопричина — не код, а АУДИО: микрофон практически не записал голос
пользователя (пиковая амплитуда ~3.6% шкалы, 97.5% сэмплов почти нулевые).
Текст в mic_transcription.txt — артефакт-галлюцинация, реального голоса
психолога в дорожке нет.

### Влияние
- Conversation теряет сторону «психолог»; статистика по психологу нулевая.
- WARNING (не FAIL) — архитектура отработала корректно, проблема во
  входных данных (аудио), а не в конвейере.
- Расхождение mic_transcription.txt (есть текст) vs mic_segments.json
  (пусто) вводит в заблуждение: транскрипт выглядит рабочим, хотя это
  галлюцинации.

### Предполагаемый способ исправления (НЕ применялось)
- Аудио (главное): проверить источник/уровень микрофона в Windows
  (устройство по умолчанию, усиление/boost, не заглушён, гарнитура vs
  встроенный). Первый тест шёл через «Microphone (Realtek…)» — вероятно
  тихий/не тот вход.
- Код (на усмотрение владельца, отдельным решением): устранить
  расхождение двух путей — либо строить Conversation и текст из ОДНОГО
  источника (сегменты), либо добавить порог/детектор «пустой дорожки»,
  чтобы галлюцинации на тишине не попадали в артефакты. Требует
  отдельного спринта и одобрения (сейчас НЕ трогаем).

## Проблема 2 — задержка первого кадра loopback 13.03 с

### Наблюдение / измерения
- mic:     record_start→first_frame = 0.10 с (норма).
- loopback: record_start→first_frame = 13.03 с.
- offsets (ADR-007): microphone=0.185s, loopback=13.029s,
  loopback−mic=12.844s.
- Длительности: mic=351.35s, loopback=319.23s (mic длиннее на 32.1 с).

### Причина
Loopback фиксирует «первый кадр» по первым реальным PCM-данным системного
вывода. 13-секундная задержка означает, что в системе ~13 с не было
выходного звука после старта захвата (звонок ещё не начался/не звучал в
динамиках). Разница длительностей (mic писал дольше с обоих концов)
согласуется: loopback реально звучал более короткий промежуток.

Это ожидаемое поведение двухпотоковой схемы (ADR-006/007): потоки
независимы, offset вычисляется объективно по first_frame_at. 13 с — не
баг конвейера, а свойство сценария записи.

### Влияние
- Большой offset loopback (13 с) корректно учитывается в timeline; порядок
  реплик и согласованность прошли PASS.
- Риск: если пользователь ожидает «синхронный старт» обеих дорожек, offset
  такого размера может удивить. На объединение/анализ пока не влияет
  (объединение не выполняется).

### Предполагаемый способ исправления (НЕ применялось)
- Процедурный (главное): начинать захват до звонка и/или проговаривать
  контрольную фразу в начале — тогда first_frame обеих дорожек ближе.
- Код (опционально, отдельным решением): фиксировать «тишину до первого
  кадра» как явное поле и/или логировать предупреждение при offset выше
  порога. Архитектуру не меняет, но требует одобрения. Сейчас НЕ трогаем.
