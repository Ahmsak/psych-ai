# ARCHITECTURE RECOMMENDATIONS — Harness Improvement Proposal

Статус: ПРЕДЛОЖЕНИЕ. Ни один файл проекта не изменён. Документ подготовлен
по Architectural Improvement Task на основе статьи «Harness engineering»
(habr.com/ru/articles/1062822/) и анализа текущей архитектуры PsychAI.

Ждёт подтверждения владельца перед любым внедрением.

---

## 0. Контекст и принцип фильтрации идей

Статья описывает «фабрику разработки» вокруг ИИ-агента: среда (роли,
гейты, аудит, откаты) важнее промпта. Ключевые переносимые идеи:
ratchet (фейл → постоянный фикс среды), sensor-first (инвариант сначала
детектором PASS/FAIL), измеримость (правило должно менять поведение).

Автор сам оговаривает: двухэтажный harness, Work Items, control plane,
портфельный слой — для ПОРТФЕЛЯ проектов. У PsychAI один продукт и один
пайплайн, поэтому эти слои НЕ внедряются (были бы избыточны). Берём
только то, что усиливает один репозиторий.

Базовая архитектура НЕ меняется:
Orchestrator — Session — Audio(capture) — Memory — LLM остаётся основой.
Все рекомендации — это слой ЗНАНИЙ и ПРОВЕРОК ВОКРУГ кода, а не
переустройство модулей.

## R1. AGENTS.md — карта проекта для ИИ-агентов

- Зачем: сейчас каждая сессия начинается с перечитывания README/ROADMAP/
  ARCHITECTURE/PHILOSOPHY и обхода структуры. AGENTS.md — открытый
  стандарт (agents.md), который агенты читают первым; сжатая карта +
  жёсткие запреты в одном месте.
- Преимущества: быстрый старт сессии; меньше дрейфа; машиночитаемый
  верхний слой над существующим START_HERE.md, без дублирования.
- Файлы: СОЗДАТЬ AGENTS.md (корень). Ссылается на docs/*, не копирует их.
- Критичность: High
- Когда: Сейчас
- Согласованность с архитектурой: нейтрально — это документация, модули
  не затрагивает.

## R2. docs/CONVENTIONS.md — кодовые соглашения

- Зачем: стиль кода (type hints, from __future__, dataclass-Config,
  приватные _методы, ресурсы в finally) соблюдается де-факто, но нигде
  не зафиксирован; агент выводит его заново каждый раз.
- Преимущества: фиксирует уже существующий стиль; опора для ratchet
  (кодовые правила пишутся сюда); снижает риск дрейфа между сессиями.
- Файлы: СОЗДАТЬ docs/CONVENTIONS.md. Не дублирует CONSTITUTION
  (там архитектурные принципы, здесь — стиль кода).
- Критичность: Medium
- Когда: Сейчас (короткий) — фиксирует статус-кво.

## R3. Единый Definition of Done (чек-лист)

- Зачем: docs/DEFINITION_OF_DONE.md уже есть, но как проза; по факту
  критерии диктуются заново каждую задачу.
- Преимущества: один чек-лист для всех задач; часть пунктов
  автопроверяема (см. R6); «push выполнен» перестаёт быть обещанием.
- Файлы: ИЗМЕНИТЬ docs/DEFINITION_OF_DONE.md (лёгкая правка к
  чек-листу). Существующий документ, не новый.
- Критичность: Medium
- Когда: Сейчас
- Единый шаблон DoD: реализовано • ограничения соблюдены • код проверен
  реальным запуском • verify_environment exit 0 • документация обновлена
  • архдокументы синхронизированы (ADR или явно «не требуется») •
  закоммичено • отправлено в GitHub.

## R4. docs/specs/ + шаблон SPEC

- Зачем: между ADR (принятые решения) и ROADMAP (план) нет слоя
  «спецификация функции ДО реализации». В Sprint 4.0 требования dual
  capture приходили частями — это дыра процесса.
- Преимущества: спека = контракт до кода; убирает приход требований
  кусками; связка SPEC → код → DoD → ADR.
- Файлы: СОЗДАТЬ каталог docs/specs/ + docs/specs/SPEC-000-template.md.
  Формат владельца: Purpose / Requirements / Constraints /
  Acceptance Criteria / Definition of Done.
- Критичность: Medium
- Когда: Сейчас (шаблон) — применять к следующей нетривиальной функции.

## R5. pytest + минимальный набор автопроверок

- Зачем: сейчас вся проверка ручная (ad-hoc скрипты в %TEMP%);
  «код проверен» держится на честном слове агента. Нет тест-раннера.
- Преимущества (sensor-first): регрессии ловятся автоматически;
  фундамент для ratchet (каждый баг → тест).
- Состав (по приоритету владельца, без усложнения):
  1. pytest каркас (pytest -q);
  2. smoke: импорт всех модулей; _rms/_resample на синтетике; создание
     конфигов без загрузки модели;
  3. проверки аудиозахвата (offline): синтез WAV-синуса → RMS>0,
     длительность верна; открытие устройств @pytest.mark.hardware;
  4. проверки транскрипции (offline): эталонный WAV в tests/fixtures/ →
     непустой текст, @pytest.mark.slow.
- Измеримые сигналы-детекторы (из вопросов 5–7):
  отсутствие транскрипции • невозможность открыть устройство •
  пустой/битый JSON • ошибки Whisper — каждый как отдельный тест
  PASS/FAIL, не смешивать с «нет аудио» (RMS≈0 — законная тишина).
- Файлы: СОЗДАТЬ tests/test_smoke.py, tests/test_capture.py,
  tests/test_transcription.py, tests/test_artifacts.py,
  tests/fixtures/, pytest.ini (маркеры hardware/slow); ДОБАВИТЬ pytest
  в requirements.txt. Существующий tests/capture_live_check.py — не
  трогать (остаётся ручной live-проверкой).
- Критичность: High
- Когда: Сейчас (smoke + offline); hardware/slow — по мере фикстур.
- Согласованность: тесты только читают публичный API модулей, границ
  Orchestrator не нарушают.

## R6. tools/check_done.py — детектор Definition of Done

- Зачем: пункты DoD «запушено в GitHub», «среда ОК», «дерево чистое»
  сейчас проверяются на глаз; самый частый источник ложного «done» —
  необъявленный незапушенный коммит.
- Преимущества (измеримость): DoD перестаёт быть обещанием; один
  вызов PASS/FAIL перед завершением задачи.
- Проверяет: git-дерево чистое; HEAD == origin/main; verify_environment
  exit 0; (опц.) pytest smoke зелёный.
- Файлы: СОЗДАТЬ tools/check_done.py. Ничего в модулях не меняет.
- Критичность: Medium
- Когда: Сейчас (после R5).

## R7. docs/RATCHET_LOG.md — журнал «ошибка → постоянный фикс»

- Зачем: реализовать принцип ratchet — каждый баг оставляет постоянный
  след в среде, а не заметку в чате.
- Преимущества: повторные ошибки ловятся средой; видна история фиксов.
- Маршрутизация следствий (без дублирования, принцип №6 конституции):
  тест → tests/ ; кодовое правило → CONVENTIONS.md ; архинвариант →
  ADR ; запрет агенту → AGENTS.md ; шаг процесса →
  DEVELOPMENT_WORKFLOW.md ; критерий → DEFINITION_OF_DONE.md.
  RATCHET_LOG.md — только индекс: Симптом | Куда лёг фикс | Дата.
- Файлы: СОЗДАТЬ docs/RATCHET_LOG.md; при внедрении — 1 строка правки
  в docs/DEVELOPMENT_WORKFLOW.md (шаг «после бага — ratchet»).
- Критичность: Low
- Когда: После MVP (полезно, но не блокирует MVP).

## R8. Согласованность с существующей архитектурой (вопрос 8)

- Базовая ось Orchestrator — Session — Audio — Memory — LLM НЕ меняется
  ни одной рекомендацией. R1–R7 — это слои документации и проверок
  ВОКРУГ кода.
- Затрагиваемые каталоги: docs/ (R1–R4,R7), tests/ (R5), tools/ (R6),
  requirements.txt (pytest). Модули capture/transcription/orchestrator/
  llm/ui/session — НЕ переписываются.
- Из статьи НЕ берём (ломало бы простоту одного продукта): двухэтажный
  harness, Work Items, control plane, ревьюеры-субагенты, eval-harness
  на каждое правило, портфельный репозиторий.
- Единственные точечные правки кода в будущем — по ratchet при реальных
  багах (try/except при открытии устройства, атомарная запись JSON,
  обёртка вызовов Whisper), и только тогда, когда баг подтверждён.

## R9. Рекомендованный порядок и статус

- Внедрять СЕЙЧАС (до продолжения MVP): R1 (High), R5 smoke (High).
- Внедрять СЕЙЧАС, лёгкие: R2, R3, R4 шаблон.
- После R5: R6.
- После MVP: R7, hardware/slow-тесты, точечные ratchet-фиксы кода.
- Deliverable-правило: массовых изменений не начинать; сначала это
  предложение → подтверждение владельца → внедрение по одному пункту
  с обычным циклом (реализовать → проверить → документировать →
  commit+push).
