# MEMORY_ARCHITECTURE — долговременная память проекта

Архитектурное предложение (Sprint 3.5). Индекс на данном этапе
НЕ реализуется — только проект решения.

## Базовый принцип (ADR-006)

Markdown — единственный источник истины. Любые индексы — производные
представления, полностью восстановимые из Markdown командой
переиндексации. Никакие знания не живут только в индексе.

## Вариант А — только Markdown (ПРИНЯТ сейчас)

Структура: START_HERE.md (корень) + docs/* + README модулей.

Преимущества:
- Ноль кода и зависимостей; работает с любым агентом и человеком.
- Git даёт версионирование, diff, blame, историю решений бесплатно.
- Невозможна рассинхронизация «индекс отстал от документов».
- Поиск: grep/ripgrep/поиск IDE достаточно при текущем объёме.

Недостатки:
- Поиск только лексический (по словам), не семантический.
- При сотнях документов навигация «по порядку чтения» перестанет
  масштабироваться.

Стоимость сопровождения: минимальная — дисциплина обновления по
DOCUMENTATION_LIFECYCLE.md. Сложность: нулевая.

## Вариант Б — Markdown + индекс (отложен)

### Б1: SQLite FTS5
- Один файл psychai_index.db (в .gitignore), таблица FTS5 по
  (path, heading, chunk). Скрипт tools/reindex.py пересобирает БД
  с нуля из docs/ за секунды.
- Преимущества: молниеносный полнотекстовый поиск, stdlib-sqlite3,
  ни одной новой зависимости, тривиальное полное восстановление.
- Недостатки: по-прежнему лексический поиск; чанкование заголовками
  нужно поддерживать.
- Сопровождение: низкое (один скрипт). Сложность: низкая.

### Б2: Векторная база (embeddings)
- Семантический поиск («где написано про завершение по Ctrl+C?»
  найдёт «graceful shutdown»). Требует модель эмбеддингов (локальную,
  из-за конфиденциальности) + хранилище (sqlite-vec / faiss / chroma).
- Преимущества: смысловой поиск, устойчив к синонимам и двум языкам.
- Недостатки: новая тяжёлая зависимость, недетерминированность,
  необходимость следить за версией модели эмбеддингов, оверкилл для
  десятка документов.
- Сопровождение: среднее/высокое. Сложность: средняя.

## Когда переходить к индексированию

Триггеры (любой из):
- docs/ + README модулей превышают ~30–50 файлов или ~200 КБ текста;
- агенту регулярно приходится читать > 5 документов, чтобы найти факт;
- появляется программная память продукта (факты сессий психолога) —
  но это ПАМЯТЬ ПРОДУКТА, отдельная от памяти проекта, и решается
  отдельным ADR.

Рекомендуемый порядок эволюции: А → Б1 (FTS5) → Б2 (векторы), каждый
шаг отдельным ADR. Начинать с Б1: 90% пользы за 5% стоимости.

## Правила для любого будущего индекса

1. Индекс пересобирается из Markdown одной командой с нуля.
2. Индекс не коммитится в git (производный артефакт).
3. Запись знаний ВСЕГДА идёт в Markdown, никогда напрямую в индекс.
4. Устаревший индекс — валидное состояние; истина всегда в Markdown.
